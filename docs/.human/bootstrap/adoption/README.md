# Adoption Sandbox

Use this route when a project already has code. The original repository stays at its own root. Create the sandbox in a separate directory; a branch in the active checkout is not isolation. A fork can supplement the separate clone when review in GitHub is useful and authorized. Do not run scripts against production, a real game save or a local installation merely because Git is isolated.

1. Record the original repository, branch, HEAD, tracked/untracked changes, native version, instructions, CI and applicable baseline checks. Identify local resources and remote side effects. Decide whether uncommitted work belongs in the adoption baseline. Prepare with `python docs/.human/bootstrap/adoption/adoption.py prepare <original> <separate-sandbox> [--include-local-changes]`. It removes the sandbox's push remote; this is a guard, not an OS permission boundary. Ignored paths, submodules, LFS data and Issues are not copied automatically.
2. Inventory existing workflow instructions, scripts, knowledge, metadata and consumers. Classify each surface as `preserve`, `adapt`, `replace`, `add`, `retire` or `conflict`. Keep useful product behavior and stronger domain rules. Promote knowledge before retiring obsolete instructions; do not erase Git history. Agree on the selected complete method and its exact delta.
3. Implement only inside the sandbox. Commit its reviewed changes there. Run the same applicable baseline checks, structural verification from the retained BootCrate tools, product checks and relevant smoke. Use `python docs/.human/bootstrap/adoption/adoption.py inspect <sandbox>` to list the committed delta and HEAD. The output is a review candidate, not acceptance.
4. After owner acceptance of that concrete delta, call `apply <sandbox> --approved-head <exact-SHA>`. It checks original HEAD/local changes and applies only the committed sandbox diff as **uncommitted changes** in the original. If the original changed, stop and reconcile; do not reset or force-push. The helper does not provision remote metadata, copy secrets, commit or publish.
5. Repeat applicable build/test/validate/run, version, CI/config, context routes, local resources and out-of-scope checks **in the original**. Review its final diff and only then perform separately authorized GitHub/commit actions. Record failures and smoke evidence in the relevant Issue. A passed sandbox is not a passed original.

This helper deliberately blocks rename/copy deltas, large local files, symlinks and ambiguous local state. Handle them as reviewed exceptions using appropriate native tools. Failure evidence is kept only as much as needed in a sanitized Issue/diagnostic; discarding a sandbox must not discard the sole explanation of a regression. Adoption is complete only when every required and selected capability actually works and conflicting old entrypoints are removed.
